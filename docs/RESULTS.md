### Stage 3: Terraform modules
**Purpose:** Write the reusable Terraform building blocks: `network`, `peering` and `eks` as separate modules with clear inputs and outputs, plus the `envs/poc` root that wires two VPCs, the peering link and two clusters together. Nothing is applied yet.

- [x] 7. `network` module: VPC, 2 public + 2 private subnets, IGW, 1 NAT per AZ, private route table per AZ, EKS subnet tags

Creates the VPC, IGW, one public and one private subnet per AZ, one EIP + NAT Gateway per AZ, a shared public route table, and one private route table per AZ defaulting to the NAT in the same AZ. Subnets carry the `kubernetes.io/role/elb`, `internal-elb` and `cluster/<name>` tags. No instances and no auto-assigned public IPs. Outputs: vpc_id, vpc_cidr_block, public/private subnet IDs, private_route_table_ids (consumed by the peering module), nat_gateway_ids, nat_public_ips. `fmt`, `validate` and `tflint` pass locally and in CI (provider resolved to aws 6.67.0).
- [x] 8. `peering` module: peering connection and cross-VPC routes in both private route tables

Public route tables are deliberately untouched. Security groups are left to the EKS module so each cluster owns its own rules. Outputs: `peering_connection_id` and `peering_status`. `fmt`, `validate` and `tflint` pass locally.

### Stage 4: Pipeline and first apply
**Purpose:** Put the Terraform behind GitHub Actions: lint and validate on every push, plan on push, apply on main. The first successful apply proves both clusters and the VPC peering exist.

- [x] 11. `ci.yml`: fmt, validate, tflint on every push

The AWS tflint ruleset is not enabled because it downloads a plugin from GitHub at runtime; noted as a possible improvement.
- [x] 12. `deploy.yml`: plan on push, apply on main
  - **RESULT:** `.github/workflows/deploy.yml` runs on every push. The `plan` job assumes the AWS role through GitHub OIDC (no static keys), runs `init` (bucket injected from the `STATE_BUCKET` variable), `validate` and `plan -out=tfplan`, prints the plan in the job summary and uploads it as an artifact. The `apply` job runs only on `refs/heads/main`, downloads that exact plan artifact and applies it, so what is applied is what was planned. Concurrency never cancels a running deploy. Verified on branch `feature/deploy-pipeline`: OIDC login works and the plan reports 70 to add, 0 to change, 0 to destroy. The apply job is skipped on branches and gets its first real run when merged to main (activity 13).
  - **Limits hit (documented for the README):** (1) OIDC was first rejected (`AssumeRoleWithWebIdentity` not authorized) because this repository uses GitHub's *immutable subject* claim (`repo:owner@ownerId/name@repoId:...`), not the plain `repo:owner/name:...` the trust policy matched. (2) The IAM user may create roles but `iam:UpdateAssumeRolePolicy` is denied, so the trust policy could not be edited in place. Fix: bootstrap now trusts both subject formats and creates a new role, `sentinel-damian-gha-v2`. (3) The old `sentinel-damian-gha` role could not be removed (`iam:DeleteRolePolicy` denied) and remains as an unused leftover. In a real environment an admin would delete it, or the role would be managed in Terraform where a trust policy change is an in-place update.
- [x] 13. First apply via GitHub Actions; both clusters ACTIVE and peering working
  - **RESULT:** Done entirely through the pipeline in two applies. Apply 1 (merge of PR #1) created 68 of the 70 resources (both VPCs, 4 NAT gateways, peering and routes, IAM roles, both EKS clusters in about 9 minutes each) and failed on the two node groups: `InvalidRequestException: Failed to validate if SLR: AWSServiceRoleForAmazonEKSNodegroup already exists due to missing permissions for 'iam:GetRole'`. Cause: the hand-written CI role policy did not allow `iam:GetRole` on `arn:aws:iam::*:role/aws-service-role/*`. Fix (PR #2): added that read permission and refreshed the policy with the bootstrap workflow. Apply 2 planned only the remaining 2 resources (the node groups) and succeeded: `Apply complete! Resources: 2 added, 0 changed, 0 destroyed.`
  - **Verified in AWS:** `eks-gateway` and `eks-backend` are ACTIVE on Kubernetes 1.35 with one managed node group each; peering `pcx-09b25e75d118de3bd` is `active` (10.10.0.0/16 to 10.20.0.0/16); 4 NAT gateways available; 4 running worker instances, none with a public IP. The Elastic IP quota was not a problem (4 EIPs allocated).

> **Stage 4 summary:** The infrastructure is deployed by the pipeline alone, nothing was applied from the laptop. `ci.yml` checks every push; `deploy.yml` plans on every push and applies the saved plan on main using keyless OIDC. Getting there exposed three real limits, all documented in `FINDINGS.md`: the immutable OIDC subject claim, the denied trust-policy edit (solved with a v2 role) and a missing `iam:GetRole` on the EKS node group service-linked role (solved by widening the CI policy). ## Day 2 – Workloads, validation, documentation


### Stage 5: Kubernetes workloads
**Purpose:** Define what runs on the clusters: the internal backend service behind an internal NLB, and the NGINX proxy behind a public NLB that forwards to the backend over the peering link. Deploy order is backend first, then gateway.

- [x] 14. Backend manifests: Deployment ("Hello from backend") + internal NLB Service with `loadBalancerSourceRanges: 10.10.0.0/16`
  - **RESULT:** Manifests in `k8s/backend/`: `namespace.yaml` (`sentinel`), `configmap.yaml` (nginx config answering `Hello from backend` on `/` and `ok` on `/healthz`), `deployment.yaml` (2 replicas spread across zones with a topology spread constraint, readiness and liveness probes, resource requests and limits, official nginx 1.27-alpine pulled from ECR Public to avoid Docker Hub rate limits) and `service.yaml` (type LoadBalancer with `aws-load-balancer-type: nlb` and `aws-load-balancer-internal: "true"`, so the NLB only has private IPs in the backend private subnets, plus `loadBalancerSourceRanges: 10.10.0.0/16`, which Kubernetes writes into the node security group). Nothing is exposed to the internet. Validated with `kubectl apply --dry-run=client --validate=strict` against the live eks-backend API (Kubernetes v1.35.8); a server-side dry-run of namespaced objects only fails because the namespace does not exist yet, which the pipeline creates first. Confirmed both backend nodes are Ready with private IPs (10.20.11.x and 10.20.12.x). Not applied yet: deployment is activity 16.
- [x] 15. Gateway manifests: NGINX Deployment + ConfigMap (backend NLB hostname via `envsubst`) + public NLB Service
  - **RESULT:** Manifests in `k8s/gateway/`: `namespace.yaml`, `configmap.yaml.tpl` (nginx reverse proxy: `/healthz` answered locally, everything else proxied to the backend NLB), `deployment.yaml.tpl` (2 zone-spread replicas, probes, limits, same ECR Public nginx image) and `service.yaml` (type LoadBalancer with `aws-load-balancer-type: nlb`, internet-facing, placed in the public subnets). The two `.tpl` files contain `${BACKEND_HOST}`, which is only known after the backend is deployed; `scripts/render-gateway.sh <host> <outdir>` renders them with `envsubst '${BACKEND_HOST}'` (only that variable, so nginx variables like `$host` are untouched). The host is also written as a pod annotation, so a changed backend address rolls the gateway pods automatically. Design choices: nginx resolves the backend name at request time (`resolver 10.10.0.2` = the gateway VPC resolver, VPC base + 2, with `set $backend` and a variable `proxy_pass`), so replacement of NLB IPs is picked up without restarting; short connect/read timeouts. Validated: the render script output passes `kubectl apply --dry-run=client --validate=strict` against the live eks-gateway API, and both gateway nodes are Ready (10.10.11.x, 10.10.12.x). Not done: a local `nginx -t` (Docker daemon not running); the proxy is exercised for real in activity 17. Not applied yet: activity 16.
- [x] 16. Deploy jobs in order: backend, wait for NLB hostname, gateway, wait for public hostname
  - **RESULT:** `deploy.yml` now has four chained jobs on main: `plan`, `apply`, `deploy-backend`, `deploy-gateway`. `deploy-backend` assumes the OIDC role, runs `aws eks update-kubeconfig` for eks-backend, applies the namespace then the manifests, waits for `rollout status`, then polls the Service until the internal NLB hostname is assigned and passes it on as a job output. `deploy-gateway` configures kubectl for eks-gateway, renders the templates with that hostname via `scripts/render-gateway.sh`, applies them, waits for the rollout and for the public NLB hostname. The first full run on main (PR merge) went green end to end with no fixes needed: plan, apply, deploy-backend and deploy-gateway all `success`.
  - **Verified in the clusters:** backend deployment 2/2 with pods on 10.20.11.248 and 10.20.12.69 (one per AZ), service type LoadBalancer with an internal `*.elb.eu-west-3.amazonaws.com` hostname; gateway deployment 2/2 with pods on 10.10.11.78 and 10.10.12.248, service with its own public NLB hostname. kubectl access works through the EKS access entry for the CI role (no aws-auth ConfigMap). The proxy-to-backend request itself is tested in activity 17.

> **Stage 5 summary:** The application layer is defined and deployed by the same pipeline that builds the infrastructure. The backend is an nginx answering `Hello from backend` behind an internal NLB restricted to the gateway VPC; the gateway is an nginx reverse proxy behind a public NLB, configured with the backend's NLB hostname injected at deploy time (`envsubst` templates, hence the strict order backend first, gateway second). Both run 2 replicas spread over the two AZs. The first complete pipeline run on main passed without changes. Not yet proven: that a request actually travels client to gateway to backend across the peering link (activity 17).

### Stage 6: Validation and bonuses
**Purpose:** Prove the system works and is restricted as designed: end-to-end curl through the public NLB, manifest and Terraform checks in the pipeline, and evidence that only the gateway VPC can reach the backend.

- [x] 17. End-to-end test: `curl` the public NLB with retries returns "Hello from backend"
  - **RESULT:** Final pipeline job `e2e-test` (after both deploy jobs) curls `http://<public NLB>/` every 15 s for up to 10 minutes (a fresh NLB can take minutes to serve) and fails the run unless the body is exactly `Hello from backend`. It passed on attempt 1 in CI (`attempt 1: 'Hello from backend'`), and the same request from my laptop earlier returned `Hello from backend` with HTTP 200. That one request exercises the whole chain: client, public NLB (internet-facing, public subnets), NGINX pod in eks-gateway, nginx resolving the backend NLB name through the VPC resolver, VPC peering route to 10.20.0.0/16, internal NLB, backend pod in eks-backend. `/healthz` on the gateway returns `ok` independently of the backend. The result is also written to the job summary.
- [x] 18. Manifest validation (`kubectl apply --dry-run=server`) and tflint wired into the pipeline
  - **RESULT:** Three layers. (1) `ci.yml`, new job `k8s-manifests`, runs on every push without any cluster: renders the gateway templates with a placeholder host and runs `kubeconform -strict` over `k8s/backend` and the rendered gateway (8 of 8 resources valid). (2) `deploy.yml` runs `kubectl apply --dry-run=server` against the real cluster API before each real apply, in both deploy jobs (output in CI: `deployment.apps/backend unchanged (server dry run)`, `service/backend unchanged (server dry run)`); the namespace is applied first because a server dry-run of namespaced objects needs it to exist. - [x] 19. Verify backend restriction (SG rule on backend nodes allows only 10.10.0.0/16) and capture evidence (CI log/screenshot)
  - **RESULT:** `scripts/verify-exposure.sh` turns the check into an automated assertion that runs in the `e2e-test` job and fails the pipeline on any violation. All 6 checks pass in CI: backend load balancer is `internal` and the gateway one `internet-facing`; no security group in the backend VPC allows inbound from `0.0.0.0/0` or `::/0`; the NLB client rule on the backend nodes allows only `10.10.0.0/16`; no running instance has a public IP; the backend NLB does not answer from outside the VPC (the runner times out). > **Stage 6 summary:** The system is proven, not just deployed.
